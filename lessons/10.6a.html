10.6a — Recursive Search: Halving the Dungeon

Discovery Lab ~40 min

You wrote binary search with a while loop in 7.3. Today you write it the way the CED wants it: recursive. And you will feel something strange happen, the same algorithm, the same halving, but the loop is gone and the method calls itself. This is the last required topic of the entire course. After today, every CED box is checked, and the sprint begins.

Experiment 1: The Story First

Your bestiary is sorted by gold value. You want the monster worth exactly 150 gold. The linear version asks every monster in order. The binary version asks a monster in the middle, and depending on the answer, throws away half the bestiary without ever asking them. Here is the recursive shape:

public static int binarySearch(int[] data, int target, int lo, int hi) {
    if (lo > hi) {
        return -1;                      // BASE CASE: empty range, not found
    }
    int mid = (lo + hi) / 2;
    if (data[mid] == target) {
        return mid;                     // BASE CASE: found it
    } else if (data[mid] < target) {
        return binarySearch(data, target, mid + 1, hi);   // right half
    } else {
        return binarySearch(data, target, lo, mid - 1);   // left half
    }
}

Do not type it yet. Trace it on paper first: data = [5, 10, 15, 20, 25, 30, 35], target 20. Draw each call: lo, hi, mid, which half survives. How many calls until "return mid"? Now target 22. Trace until the base case. Where does it end up? (lo crosses hi: 3 > 2. Return -1.)

Experiment 2: Now Type It and Instrument It

Create RecursiveSearchLab.java. Type the method. Then add a print at the top: System.out.println("search(" + lo + ", " + hi + ")"); and run searches for the first, middle, last, and a missing element on a sorted array of 1000 elements. Read the call trail. Each call's range is half the previous. 1000 to 500 to 250 to 125... The trail IS the log n you were promised in 4.7a. Count the calls for each search and put them in your table next to the linear counts from 4.7a.

The three exam traps, all in one method:
1. mid + 1 / mid - 1, never mid. If the recursive call includes mid, ranges stop shrinking and you get infinite recursion. Try it: change mid + 1 to mid and search for a missing value. Watch the StackOverflowError. Feel it. Put it back.
2. Both base cases are mandatory. Found (return mid) and not-found (lo > hi, return -1). Miss either one and the method never terminates.
3. The data must be sorted. Same rule as the loop version. Binary search on unsorted data returns garbage confidently.

Experiment 3: Search Your Bestiary

Back to the RPG. Load monsters.txt, build an int[] of gold values, sort it with your 10.3 merge sort (or selection sort, if you want to feel the speed difference), then write findMonsterByGold(int target) on top of recursive binary search. Which monster is worth exactly 150 gold? Now time both searches on 8 entries, then imagine the bestiary at 8 million: one search reads every entry, the other reads 23. (log2(8,000,000) is about 23. Two to the 23rd is about 8 million. You now own this fact.)

Bug Hunt: Break the Recursion

Three broken variants are in the recursive search docs. One loops forever (bad bounds), one skips elements (mid vs mid+1 mixed up on one side only), one returns the wrong index type entirely. For each: predict the symptom, run it, confirm, fix. Infinite recursion prints a wall of your own trace lines before dying. It is the loudest bug in Java and it is unforgettable.

Socratic Checkpoint

  1. In one sentence: why must the recursive call use mid+1 or mid-1 and never plain mid? Use the word "smaller."
  2. The loop version and the recursive version do identical work. Same step counts, same halving. So why does the CED care about the recursive one? (What can recursive binary search do that the loop cannot generalize to? Think about what else gets halved: quicksort's partitions, tree walks, flood fill.)
  3. Last CED check of the year: topic 4.17 is "Recursive Searching and Sorting." You have recursive binary search and recursive merge sort. Write in your notes: one thing recursion finally made click, and one thing you still want to drill before the mock. Bring the second one to the clinics.

Checkpoint — before moving on, you must be able to:

  • Write recursive binary search with both base cases, from memory
  • Trace a search on paper, showing lo/hi/mid per call
  • Explain and demonstrate the mid vs mid+1 infinite-recursion bug
  • State the log n call count for 1000 and 1,000,000 elements
