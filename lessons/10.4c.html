10.4c — Procedural Dungeon & Course Retrospective

RPG Build ~35 min

You built flood fill. You built shortest path. Now combine them into a procedural dungeon generator — a system that guarantees every dungeon is solvable, then use your map tools to prove it. This is the final RPG activity of the course. Everything you've built across 10 units comes together here.

Part 1: Guaranteed Solvable — The Post-Generation Check

Add a generate() method to DungeonMap that creates a random map AND verifies a path exists before returning it:

public void generate(int rows, int cols) {
    do {
        randomFill(rows, cols);  // fill with random walls/floors
        placePlayerAndExit();     // place 'P' and 'E' on floor tiles
    } while (!hasPath());        // regenerate if no path exists
}

The condition for hasPath(): your reveal() from 10.4a starts at the player's tile. If it doesn't count the exit tile, no path exists. Use your own flood fill to validate the generation.

Socratic Checkpoint

  1. Why do we need the do-while loop? What would happen without it — could the player ever be stuck in a dungeon with no exit?
  2. Your dungeon generation involves: Math.random() (Unit 1), loops (Unit 4), arrays (Unit 6), 2D arrays (Unit 8), and recursion (Unit 10). Map each piece to where you learned it. How many units of knowledge power this one method?

Part 2: The Difficulty Ramp

Add a difficulty parameter to your generate() method. Higher difficulty adds more obstacles:

  • Easy: 20% walls, exit within 10 steps, small map (8×8)
  • Medium: 35% walls, exit 15–25 steps away, medium map (12×12)
  • Hard: 50% walls, exit 25+ steps away, large map (15×15)

Use shortestPath() from 10.4b to measure the distance. If the path is too short or too long for the difficulty, regenerate. Now every map feels fair.

Tinker: Dead-End Detection

The most frustrating dungeons have long dead-end corridors. Use flood fill to identify tiles that have exactly one reachable neighbor. Mark dead ends with a different symbol in your fog-of-war display so players can avoid them. Bonus: place loot at the end of dead ends to reward exploration.

Socratic Checkpoint — The Final Reflection

  1. Pick three units. For each one, describe what your RPG engine would be missing if you had skipped that unit.
  2. Unit 1 seems trivial now (just Math.random() and printing). But every following unit depends on it. If a new student asked you "why do we spend so much time on random numbers?", what would you tell them?
  3. Your DungeonCrawl.main() orchestrates everything: generate a map, place the player, loop through rooms, run combat, manage inventory, reveal fog of war, find paths. How many classes does it use? How many objects? Trace one full game loop and count everything it touches.
  4. You started this course having never compiled code. You're ending it with a procedural dungeon generator that self-validates using recursive algorithms. What's one thing you understand now that seemed impossible in September?
  5. What would you build next? Given everything you now know, what game mechanic or system would you add to this engine?

Final Checkpoint — your complete RPG engine must:

  • Generate guaranteed-solvable dungeons (flood fill validation)
  • Display fog of war (reveal) and shortest path (compass)
  • Run a complete game loop: map → rooms → combat → loot → inventory → next room
  • Support at least 3 difficulty levels with appropriate path lengths
  • Use every class you've built across all 10 units
