5.5c — Player vs Monster: Boss Fight & Unit 5 Retrospective

RPG Build ~30 min

You built Player. You built Monster. You rewired DungeonCrawl to use both. Now prove it all works — and reflect on what encapsulation actually bought you.

Part 1: The Boss Fight Test

Add a boss room to your DungeonCrawl. When the player reaches the final room of the final floor, they face:

Monster boss = new Monster("Dragon", 80, 80, 18, 8, 12);  // d12 attack!

Requirements:

  • The boss fight uses the same runCombat() method as every other encounter
  • Before the fight, print the boss's toString() — the player should feel dread
  • If the player wins, print a victory message and a final stats summary
  • If the player dies, print "GAME OVER" with the dungeon floor they reached

Socratic Checkpoint

  1. Your boss is created with one line. Your old code needed six lines for a monster (name, hp, maxHp, ac, attackBonus, damageDie all separate). What changed? Why does this matter?
  2. The boss is a Monster just like a Goblin. What design principle lets you treat a Dragon and a Goblin the same way in your game loop?

Part 2: Systematic Testing — Prove Your Classes Work

Create a PlayerTest.java that proves every method works correctly. Write one test per method. Each test prints what it's testing and whether it passed.

===== Player Tests =====
Test 1 — Constructor: Hero [HP: 25/25 AC:14 STR:12]  ✓
Test 2 — takeDamage(10): HP now 15  ✓
Test 3 — takeDamage(30): HP 0, isAlive=false  ✓
Test 4 — heal(10): HP 10, isAlive=true  ✓
Test 5 — heal(25): HP 25 (clamped to maxHp)  ✓
Test 6 — takeDamage(-5): HP 25 (negative damage handled)  ✓
===== 6/6 tests passed =====

Do the same for MonsterTest.java. Edge cases matter: damage at exactly 0 HP, healing at max HP, negative damage, negative heal amounts.

Socratic Checkpoint — Unit 5 Retrospective

  1. You've been building programs since Unit 1. This is the first time you've built separate classes with private fields and public methods. What do you understand now that you couldn't explain in Unit 1?
  2. In your test code, you call player.takeDamage(30) and then player.isAlive(). Notice you never touched the hp field directly — and you COULDN'T if you tried. Why is that a good thing?
  3. DungeonCrawl's runCombat() used to take 8+ parameters. Now it takes 2. Count the total lines in your DungeonCrawl before and after encapsulation. Where did the code go?
  4. In Unit 6, you'll build an inventory system. Given what you now know about classes, how would you design an Item class?

Part 3: Encapsulation — What It Bought You

Write answers in a journal or discuss:

  1. Before — your code had scattered variables (int playerHP; String playerName;). Every method that needed player data took 4+ parameters. Describe what was painful about this.
  2. After — one Player object, one Monster object. Methods take 2 objects instead of 8 values. Describe what's better.
  3. Next — in Unit 9, you'll learn inheritance. Player and Monster share so much code. What would a shared GameCharacter class look like?

Checkpoint — before moving on to Unit 6, you must be able to:

  • Design a class with private fields, constructor, getters, and mutators
  • Write systematic tests that verify every method
  • Replace scattered variables with encapsulated objects — and explain why it's better
  • Trace code that crosses class boundaries (Player in DungeonCrawl, Monster in Combat)
