5.6a — Design From a Spec: Building to Contract

Expand Application ~45 min

Free-response Question 2 hands you a scenario and a specification table, and says: build the class. No example code. No starter file. The spec IS the documentation. This is also, not coincidentally, how professional software gets built. Today you do the whole cycle in one sitting: read the spec, plan the class, implement, test against the acceptance table, iterate.

The Spec: class Spell
A Spell has a name, a mana cost, and a damage value.

Constructor: Spell(String name, int manaCost, int damage)
Methods:
MethodBehavior
getName()returns the name
getManaCost()returns the mana cost
getDamage()returns the damage
isAffordable(int manaAvailable)true when the spell's mana cost is at most manaAvailable
cast()returns damage, but only if the caster can pay: takes no parameters here, just returns the damage value (we will wire mana logic in the challenge)
toString()"Fireball (cost 30, damage 25)" using the actual field values

Step 1: Plan on Paper First

Before touching the keyboard, write in your notes:

  • The fields: names AND types. (Three fields. Which are private?)
  • The constructor: what it assigns.
  • Method by method: what goes in, what comes out, which fields it touches.

Show the plan to another student. Compare. Argue about field names if you must. Then, and only then, open the editor.

Step 2: Implement and Test Against the Table

Write Spell.java. Then SpellTester.java with this acceptance table. Every row must pass:

Spell fireball = new Spell("Fireball", 30, 25);
Spell heal = new Spell("Heal", 10, 0);

fireball.getName()        // "Fireball"
fireball.getManaCost()    // 30
fireball.isAffordable(40) // true
fireball.isAffordable(20) // false
heal.getDamage()          // 0
fireball.toString()       // "Fireball (cost 30, damage 25)"

Print each result and compare by eye. One row will probably fail on the first pass. That is normal and that is the point of the table.

Step 2.5: Javadoc the Contract

Every method you wrote in 2.8b style: @param where there are parameters, @return where there is a return value. Two minutes of writing, and your class now reads like the JQR.

Step 3: Spec Review (the real skill)

Swap computers with a partner. Your job: find where their class violates the spec. Check in this order:

  1. Types: is isAffordable really boolean?
  2. Edges: isAffordable(30) exactly at the cost. Does it return true? The spec says "at most," so true is correct. Off-by-one here is the most common spec violation in real code review.
  3. toString: exact format, parentheses and commas included?
  4. Privacy: are the fields private? Can you find any way to change damage without a method?

Report findings as a list. Fix what your reviewer found. Re-run the table. This loop, implement, review, fix, is the daily rhythm of every software job.

Step 4 (Challenge): The Shopkeeper's Spec

Now the reverse direction, alone. Design the spec table for a Potion class a partner will build from YOUR table: name, price, potency, and behavior of your choosing (at least four methods). Write only the table, no code. Trade with a partner and build each other's. The hardest part of design is writing an unambiguous table. Discover that firsthand.

Socratic Checkpoint

  1. Which was harder: building from the spec, or writing the spec for someone else? What did the spec-writing reveal about ambiguity?
  2. The spec said "at most manaAvailable." Rewrite that phrase in your own words as a Java expression. Why do spec authors use English instead of code? What is gained, what is risked?
  3. Look at a real FRQ 2 from the exam hub. The table you just used is formatted exactly like the exam's. What did this lesson make less scary?

Checkpoint — before moving on, you must be able to:

  • Translate a spec table into fields, constructor, and methods without example code
  • Build an acceptance test table and verify each row
  • Review another student's class against a spec, checking types, edges, format, and privacy
  • Write an unambiguous spec table for a class of your own design
