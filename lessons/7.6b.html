7.6b — Save Games & High Score Files

RPG Build ~40 min

Yesterday you loaded monsters. Today the file work turns inward: your own game state. A roguelike where death erases everything is honest, but a game that remembers you between runs is a relationship. You will build the persistence layer of your RPG: character save files and a persistent high score table.

Part 1: The Save File Format (design it yourself)

Decide your save format for a Player: name, class, level, hp, maxHp, gold, and your inventory item names. Write a sample save by hand first, on paper, exactly as your game will print it. Two rules from 2.9a apply: pick ONE delimiter and stick to it, and design so a loader can guard against bad lines. Then make your game print it:

$ java Game > save.txt

Open save.txt in your editor and check it against your paper design. Then close it and write the loader in your game: read save.txt if it exists, rebuild the Player and the inventory, and drop the player back into the dungeon with their stats intact.

The existence check: your game should not crash when there is no save yet (first run). Structure:

File f = new File("save.txt");
if (f.exists()) {
    // load
} else {
    // fresh start: character creator
}

exists() is not on the JQR but it works and it is the right instinct. First-run experience: designed, not crashed into.

Part 2: The Persistent High Score Table

A high score file that survives restarts. Format, one entry per line:

Aram,Warrior,14200
Kai,Rogue,9800
Sam,Mage,7300

Build HighScores.java with this contract:

  • load() — reads scores.txt into an ArrayList of entries (parallel ArrayLists of name/class/score, or an Entry class if you are feeling strong)
  • addScore(String name, String cls, int score) — inserts in sorted position (highest first) using your 7.3 algorithms
  • display() — prints the table with rank numbers
  • isHighScore(int score) — true if the score would make the top 10
  • save() — prints the table back out with $ java Game > scores.txt or by printing top-10 lines to a save file your loader reads next run

Celebrate a run by adding a fake score, saving, restarting, loading, and finding it on the board. Persistence across process death is the moment a program becomes a world.

Bug Hunt: The Corrupt Save

Corruption is a save-file's natural predator. Test your loader against these, one at a time. It must survive all of them without crashing:

  1. Empty save.txt (zero bytes)
  2. A save with one line missing a field ("Aram,Warrior" and nothing else)
  3. A save with garbage numbers ("Aram,Warrior,lots,0,0,0")
  4. A high score file with 15 entries (your top-10 logic must handle it)
  5. The trickiest: a player named "A,ram" (the delimiter inside the data!)

For each: what SHOULD happen? Fresh start with an apology? Skip the line with a warning? Your guard clauses from 6.6b decide. For the delimiter-in-data problem, there is no perfect fix with split; write one sentence in your notes on how you would design the format to avoid it (hint: what character can never appear in a name?).

Socratic Checkpoint

  1. Your save format and monsters.txt were both designed by someone. What makes a file format good? Write three rules. (Ideas to consider: one record per line, fields in a fixed order, documented delimiter, no data that contains the delimiter.)
  2. The high score file is shared data: every run of the game by every player reads and writes it. What happens if two runs write at the same time? You do not have the tools to solve this yet, so just name the problem correctly in your notes. (Concurrency. It is a whole college course. Naming it is enough today.)
  3. AP exam check: your loader loop is "while hasNext, nextLine, split, parseInt, add." Write that loop from memory, right now, no notes. If you hesitated, you know what to drill before the mock.

Checkpoint — before moving on, you must be able to:

  • Design a save-file format and defend its rules
  • Implement load/add/display/save for a persistent score table
  • Survive all five corruptions with guard clauses and good defaults
  • Write the file-loading loop from memory under time pressure
