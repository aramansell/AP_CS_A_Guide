8.6a — Dungeon Maps From Files

RPG Build ~45 min

Unit 8 gave you the grid. Unit 7.6 gave you files. Today they merge into the most satisfying structure in the whole course: a dungeon map that loads from a text file, where every wall, floor, monster, and the player position is just a character in a text file you can edit. Level design becomes text editing.

Download the maps first. dungeon1.txt (small tutorial map) and dungeon2.txt (the real dungeon). Legend: # wall, . floor, @ player start, G goblin, spaces outside the walls mean nothing. Open both in tabs and read them with your eyes first. Can you find the goblin? Can you see the path from @ to G?

Part 1: Load the Map

Create DungeonLoader.java. The pattern is a direct upgrade of 7.6a: each line of the file is a ROW of the grid.

import java.util.Scanner;
import java.io.File;

Scanner in = new Scanner(new File("dungeon1.txt"));

// Pass 1: count the rows
int rows = 0;
while (in.hasNext()) { in.nextLine(); rows++; }
in.close();

// Reopen and fill
in = new Scanner(new File("dungeon1.txt"));
char[][] map = new char[rows][];
int r = 0;
while (in.hasNext()) {
    map[r] = in.nextLine().toCharArray();
    r++;
}
in.close();

Run it and print the map with nested loops to prove it loaded. Then answer: how many columns does row 0 have? Does every row have the same length? (Check with code: map[r].length. If they differ, your bounds checking must use map[r].length per row, not one fixed width. This is the jagged-array trap, and the CED tests it.)

Why two passes? You need the row count before you can create the array. The reopen trick (close, new Scanner) is the simple solution. An ArrayList of char[] would skip the counting pass entirely. Build it once each way; feel the difference.

Part 2: Find the Features

Write find(char target) that scans the grid and returns the row and column of the first match (print them, or return an int[] {row, col}). Find @. Find G. Then write count(char target): how many walls? How many floor tiles? And a printLegendCounts() that prints a little census of every character in the map. Your 8.2 traversal patterns, now with meaning.

Part 3: Level Design Is Text Editing

Copy dungeon1.txt to dungeon3.txt in your folder. Redesign it: move the goblin, extend a corridor, add a second goblin (g), add a treasure room with $. Do not touch your Java. Run the loader on dungeon3.txt. It just works. That feeling, of the world changing because you edited text, is the entire point of data-driven design. Now load dungeon2.txt and count the goblins: is one hiding in a pocket you did not notice?

Bug Hunt: The Map That Ate Itself

  1. Remove the in.close() between the two passes and reopen without a fresh Scanner. What happens? (The second loop reads nothing: the scanner is at end-of-file. Your map is all nulls and everything crashes.)
  2. Trailing whitespace: add two spaces after the last wall on some row. Now row lengths differ by 2. Which of your loops, if any, breaks? (Printing survives; anything assuming fixed width does not.)
  3. Empty line at the end of the file: some editors add one. Then map[last] is an empty array. Guard it: skip lines of length 0 when filling.

Socratic Checkpoint

  1. Why is data-driven level design better than generating maps in code? Give the designer argument and the modder argument, then check your answer against the 7.6a Socratic. Same argument, bigger stakes.
  2. Your map loader uses nextLine + toCharArray. The JQR also offers next(). What would the map look like if you read it with next() instead of nextLine()? Try it on dungeon1.txt and see what breaks. (Spaces are delimiters to next(). Maps are made of spaces. Catastrophe.)
  3. Exam connection: FRQ 4 gives you a 2D array and asks you to traverse and process it. Your census, find, and count methods ARE FRQ 4 methods. Which one maps to "count occurrences in a grid"? Which to "locate a target"?

Checkpoint — before moving on, you must be able to:

  • Load a text-based map into a char[][] with the two-pass pattern
  • Handle jagged rows with per-row bounds checking
  • Write find/count/census methods over a loaded grid
  • Explain data-driven design and defend it
