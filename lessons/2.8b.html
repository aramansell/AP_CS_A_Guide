2.8b — Documentation with Comments: Write for Your Future Self

Basic Application ~20 min

The AP exam's Practice 4, "Document Code and Computing Systems," is worth 10-15% of the multiple-choice section. College Board is not grading your comments for beauty. They are testing whether you can read a program's intent, and whether you can leave intent behind for the next person. The next person is usually you, three weeks later, at 11 PM.

Experiment 1: The Three Comment Flavors

Create CommentsLab.java and type all three comment styles:

// Line comment: one line, quick notes

/* Block comment: spans
   multiple lines. Older style. */

/**
 * Javadoc comment: the special one. Starts with /**
 * and every line has a star. This is documentation
 * that TOOLING can read. Hover your mouse over a call
 * to this method in your editor and see what appears.
 */
public class CommentsLab {
    // the rest of your code
}

Type it, then hover over the class name where you use it. Editors read the javadoc and show it back to you. That is the difference between javadoc and ordinary comments: javadoc is machine-readable documentation.

Experiment 2: Document Your Dice Engine

Open your Dice.java from Unit 1. Add a javadoc block above roll() with exactly this structure:

/**
 * Rolls a single die with the given number of sides.
 * @param sides the number of sides on the die (must be 2 or more)
 * @return a random int between 1 and sides, inclusive
 */
public static int roll(int sides) { ... }

Do the same for rollDice and isCritical. Then call Dice.roll(20) from your tester and hover. Your own words are now official documentation, exactly like Math.abs.

@param documents what goes in. @return documents what comes out. One line each. Present tense. Describe behavior, not implementation ("returns the higher roll" not "calls roll twice and compares"). If a method has no parameters, there is no @param. If it returns void, there is no @return.

Bug Hunt: Lying Comments

Comments that do not match code are worse than no comments. From the comments docs page, grab the four code-and-comment pairs. In each, the comment says one thing and the code does another. Find the lie, then fix the comment (or the code, if the comment was right all along). The lies are subtle: off-by-one, wrong bounds, "random" where it is deterministic.

Socratic Checkpoint

  1. Find the worst comment you have written all year (we all have one). What made it bad: it lied, it said nothing, or it repeated the code?
  2. Here is a comment: // set x to x plus 1 above x++. Delete-worthy or keep-worthy? Defend your answer with a rule.
  3. The JQR sheet you used in 2.8a is generated FROM javadoc comments. When you wrote @param and @return today, you were doing the same job Oracle's writers do for the whole Java library. Does that change how you think about the sheet?

Checkpoint — before moving on, you must be able to:

  • Write all three comment types and say when each is appropriate
  • Write a correct javadoc block with @param and @return for any method
  • Spot a comment that contradicts its code
  • Explain why "Document Code" is a scored exam practice
