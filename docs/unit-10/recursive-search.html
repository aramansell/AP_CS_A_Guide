Recursive Search & Merge Sort

CED topic 4.17, the last required topic of the course: binary search written recursively, and merge sort, which only makes sense recursively. Both share one heartbeat: cut the problem in half, solve the halves, trust the recursion, combine.

Recursive Binary Search

// PRECONDITION: data is sorted ascending
public static int bsearch(int[] data, int target, int lo, int hi) {
    if (lo > hi) return -1;                  // base case 1: empty range
    int mid = (lo + hi) / 2;
    if (data[mid] == target) return mid;     // base case 2: found
    if (data[mid] < target)
        return bsearch(data, target, mid + 1, hi);   // right half
    else
        return bsearch(data, target, lo, mid - 1);  // left half
}

// call it like this: the whole array, initially
int index = bsearch(data, target, 0, data.length - 1);

Why it is recursive at all: each call handles one question ("is the target in THIS range?") and delegates the smaller question to itself. The loop version asks the same question repeatedly with updated lo and hi. Same work, different bookkeeping: the loop updates variables, the recursion passes them forward.

Two calls, and the answer bubbles back up unchanged: each parent returns exactly what the child returned. When every level just passes the answer up, that is "tail-ish" recursion, and it means the loop version is a mechanical rewrite. The exam may ask you to do that rewrite in either direction.

Merge Sort: Divide, Sort Halves, Merge

public static void mergeSort(int[] data, int lo, int hi) {
    if (lo >= hi) return;                    // base case: 0 or 1 elements = sorted
    int mid = (lo + hi) / 2;
    mergeSort(data, lo, mid);                // sort left half
    mergeSort(data, mid + 1, hi);            // sort right half
    merge(data, lo, mid, hi);                // merge two sorted halves
}

The merge is the only part with real code, and it is a two-finger walk:

private static void merge(int[] data, int lo, int mid, int hi) {
    int[] temp = new int[hi - lo + 1];
    int i = lo, j = mid + 1, k = 0;

    while (i <= mid && j <= hi) {             // both halves have items
        if (data[i] <= data[j]) temp[k++] = data[i++];
        else                    temp[k++] = data[j++];
    }
    while (i <= mid) temp[k++] = data[i++];   // drain left leftovers
    while (j <= hi) temp[k++] = data[j++];    // drain right leftovers

    for (k = 0; k < temp.length; k++)          // copy back
        data[lo + k] = temp[k];
}

Why Merge Sort Is n log n (Informally)

Two facts: halving n down to 1 takes about log n levels, and each level touches every element once during its merges. log n levels times n work per level: n log n. Compare with selection sort's n squared: at a million items, merge sort does about 20 million moves, selection sort about 500 billion. That is the difference between instant and never. This is 4.7a's analysis applied, and it is why "merge sort exists" is exam knowledge, not trivia.

The Three Recursive Sins (all three break search and sort)

No base casemissing lo > hi check: infinite recursion, StackOverflowError missing lo >= hi check: mid+1 bounds walk off the array

Forgetting the combine(not applicable; search just returns)sorting halves but never merging: array unchanged and you conclude "recursion is broken" (it is not; the merge is)

Bug Hunt: Three Broken Variants

Find the Symptom Before You Run

// A
public static int bsA(int[] d, int t, int lo, int hi) {
    int mid = (lo + hi) / 2;
    if (d[mid] == t) return mid;
    if (d[mid] < t) return bsA(d, t, mid + 1, hi);
    return bsA(d, t, lo, mid);
}

// B
public static int bsB(int[] d, int t, int lo, int hi) {
    if (lo > hi) return -1;
    int mid = (lo + hi) / 2;
    if (d[mid] == t) return mid;
    return bsB(d, t, lo + 1, hi);
}

// C
public static int bsC(int[] d, int t, int lo, int hi) {
    if (lo > hi) return -1;
    int mid = (lo + hi) / 2 + 1;
    if (d[mid] == t) return mid;
    if (d[mid] < t) return bsC(d, t, mid + 1, hi);
    else return bsC(d, t, lo, mid - 1);
}

A: the else-branch recurses with plain mid, so an absent target in the left half loops forever between two indices. Symptom: stack overflow on missing values, works on found ones. B: it advances lo by 1 regardless of side: a linear search in disguise that also misses the midpoint logic; symptom: returns -1 for values that exist. C: mid is shifted one right; when lo == hi, mid = lo + 1 can read past the range and even out of bounds at the right edge; symptom: ArrayIndexOutOfBounds on single-cell ranges, or skipped odd indices. Predict, run, confirm each. Then fix all three and re-verify against the trace table above.

Tinker Challenge: Feel the Speed Difference

Time the Sorts

Fill an int[] of 20,000 with random values. Time selection sort (System.currentTimeMillis() before and after). Restore the array (regenerate the same randoms with a fixed seed, or keep a copy), then time merge sort. Record both numbers. Now double to 40,000 and repeat. Selection should take about 4x longer (quadratic: 2 squared). Merge sort about 2.2x (n log n: barely worse than linear). Your table is 4.7a's shapes, now with clocks on them.

Socratic Checkpoint

Why must merge sort be recursive in this course?

It is not that iterative merge sort is impossible (it is, with a stack and a loop). It is that the recursive description IS the algorithm: sort halves, merge. The recursive code is four lines that read like the English. For once, the recursive solution is the simplest one, and that is why the CED put merge sort in the recursion topic: it is the exhibit that recursion is not just a loop alternative, it is a decomposition strategy.

Why does binary search return from EVERY path?

Because each call must produce an answer to hand its caller. The three returns are the three truths of the range: not here (-1), found here (mid), not in this half (whatever the recursive call returns). Miss a return path and Java refuses to compile, which is the compiler enforcing that you have thought about every case. That enforcement is a gift; accept it.
