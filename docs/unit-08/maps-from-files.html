Dungeon Maps From Files

The capstone pattern of the data side of the course: a text file becomes a char[][] becomes a world. File reading (7.6) + 2D arrays (Unit 8) + a toCharArray trick that turns a String into a row of characters. When this works, level design becomes text editing, and your game stops being a program and becomes a platform.

The Map Format

########
#......#
#.####.#
#.#G.#.#
#..@...#
########
CharacterMeaning
#wall (impassable)
.floor (walkable)
@player start
Ggoblin
$treasure (8.6's extension)

One line per row. Row 0 is the top. Column 0 is the left edge. No commas, no spaces inside the map: every character is terrain.

The Two-Pass Loader

import java.util.Scanner;
import java.io.File;

// Pass 1: count rows (you need the number BEFORE you can create the array)
Scanner in = new Scanner(new File("dungeon1.txt"));
int rows = 0;
while (in.hasNext()) { in.nextLine(); rows++; }
in.close();     // MANDATORY: resets the file position by releasing the handle

// Pass 2: reopen and fill
in = new Scanner(new File("dungeon1.txt"));
char[][] map = new char[rows][];
int r = 0;
while (in.hasNext()) {
    String line = in.nextLine();
    if (line.length() > 0) {          // guard: skip trailing blank lines
        map[r] = line.toCharArray();
        r++;
    }
}
in.close();

toCharArray() is the magic line: it converts a String into a char[], one char per index. It is not on the JQR, but it is standard Java and the natural bridge from line to grid.

Why two passes? Creating new char[rows][] requires knowing rows, but you only learn rows by reading. Options: count then reopen (above), or skip the count with ArrayList<char[]> and copy out afterward. The ArrayList version is cleaner and is what 7.6b's load() pattern suggests. The two-pass version is what 8.6a trains, because seeing WHY the count is needed teaches you something about arrays that ArrayList hides.

Jagged Rows Are Normal

Nothing forces every line of the file to have the same length. If a designer types one fewer wall, that row is one shorter. Your code must use map[r].length per row, never a single width constant. This is not defensive paranoia; the CED explicitly includes jagged arrays in its 2D array topics, and 8.6a's bug hunt makes you meet the problem in a real file.

The Census, Find, and Count

// find: locate a marker
public static int[] find(char[][] map, char target) {
    for (int r = 0; r < map.length; r++)
        for (int c = 0; c < map[r].length; c++)
            if (map[r][c] == target) return new int[]{r, c};
    return new int[]{-1, -1};
}

// count: census of one character
public static int count(char[][] map, char target) {
    int n = 0;
    for (int r = 0; r < map.length; r++)
        for (int c = 0; c < map[r].length; c++)
            if (map[r][c] == target) n++;
    return n;
}

These two are FRQ 4 in miniature: traverse, compare, act. Everything bigger (fireball boxes, neighbor counts, movement) is these plus the 2d-algorithms patterns.

Movement On a Loaded Map

// attempt to move '@' by dr rows and dc columns
public static void move(char[][] map, int dr, int dc) {
    int[] pos = find(map, '@');
    int r = pos[0], c = pos[1];
    int nr = r + dr, nc = c + dc;

    // three guards, in order: inside the grid, then walkable
    if (nr < 0 || nr >= map.length) return;
    if (nc < 0 || nc >= map[nr].length) return;
    if (map[nr][nc] != '.' && map[nr][nc] != 'G') return;   // wall check

    map[r][c] = '.';        // erase old position
    map[nr][nc] = '@';      // stamp new position
}

Bounds, then terrain, then the swap. That sequence is every grid game ever written, and every Season 2 project (fog of war, maze solver, pathfinding) reuses it unchanged.

Tinker Challenge: Ship a Level Pack

Three Maps, One Engine

  1. Design dungeon3.txt yourself: at least 12x12, one goblin, one treasure room with '$', and a wall shape that forces a detour.
  2. Write loadMap(String filename) that takes any map filename and returns the grid. Same engine, any level.
  3. Write a main that loads all maps in sequence and prints, for each: size, wall count, floor count, goblin positions, treasure count, and whether '@' exists (a missing '@' is a level design bug: report it, do not crash).
  4. Swap maps with a partner. Playtest theirs by reading the census: can you spot a sealed-off treasure room from the numbers alone? (Sometimes. That is a reachability question, which is what Season 2's flood fill answers definitively.)

Bug Hunt

The Missing Close

Remove the in.close() between the two passes and re-run. Pass 2 reads ZERO lines (the scanner sits at end-of-file from pass 1), your map is all nulls, and the first map[r].length throws a NullPointerException. The error is far from the cause. Trace it back. This is why "always close" is a rule rather than a suggestion.

The Invisible Short Row

Open your map file and delete one character from a middle row. Print the map. It renders fine (strings are just shorter), but any fixed-width logic (column sums assuming equal rows, movement checking nc < width) now reads the wrong cell or crashes. Fix by using per-row lengths everywhere, then break it again on purpose to see which of your methods trusted the constant. Now you know which of your methods would fail a code review.

Socratic Checkpoint

Why is data-driven design the payoff of the whole data sequence?

4.2 (datasets) taught records. 4.6 (files) taught loading. 4.11-4.13 taught grids and algorithms. This page is 4.6 + 4.11 combined into the thing they were all for: worlds described by data, engines that process any world matching the format. The moment content moves out of code, your program stops being an artifact and becomes a platform. That is the professional threshold, and you cross it with a text editor.

Why char[][] instead of String[]?

Strings are immutable: you cannot stamp '@' into a new cell without rebuilding the whole row. A mutable grid needs mutable cells, so chars it is. The cost is toCharArray and char comparisons; the payoff is that movement, fireballs, and fog of war are single assignments instead of string surgery.
